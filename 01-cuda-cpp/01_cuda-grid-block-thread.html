1 The Problem: Why GPUs?

Suppose you need to add two 128×128 matrices: C = A + B. That's 16,384 independent additions. On a CPU, you process them one by one in a loop. On a GPU, you launch one thread per element — all running simultaneously.

Key insight: Each addition is completely independent — C[i][j] only needs A[i][j] and B[i][j]. This is embarrassingly parallel: the perfect use case for a GPU.

2 The Big Idea: One Thread Per Element

Instead of writing a loop, you write a kernel function that describes what one thread does. Then you tell CUDA: "launch 16,384 copies of this function, each knowing its own position in the matrix."

But 16,384 is a lot of threads to manage. CUDA doesn't just dump them all in a flat list — it organizes them in a hierarchy that matches the shape of your data.

The mental model shift: Stop thinking "loop over elements." Start thinking "every element is a worker that runs the same code with a different address."
↓

3 The Three-Level Hierarchy

CUDA organizes threads in three nested levels. Think of it like a factory floor:

🏭
Grid
= The entire factory
The full production order. All workbenches running in parallel to complete the job.

Our example: 16×16 = 256 workbenches
🛠
Block
= One workbench
A team of workers that share the same toolbox (shared memory) and can coordinate with each other. Workers at different benches cannot.

Our example: 8×8 = 64 workers per bench
🧑‍🏭
Thread
= One worker
Picks up exactly one piece, performs the operation, puts it down. Same skill, different piece.

Our example: computes one C[r][c]

Why blocks matter: Threads within a block are special — they run on the same Streaming Multiprocessor (SM) and can:

  • Share fast memory — ~100× faster than global GPU memory (48–228 KB of shared memory per SM)
  • Synchronize — barrier sync with __syncthreads()
  • Exchange data — cooperate on sub-problems like tiled matrix multiplication

Threads in different blocks cannot do any of this. The block is the unit of cooperation.

↓

4 dim3: Shaping Your Parallelism

CUDA uses a type called dim3 to define thread organization. It always has three components (x, y, z), but unspecified dimensions default to 1. One type handles 1D, 2D, and 3D problems:

CUDA C++ dim3 a(256); // 1D: 256 × 1 × 1 → audio, 1D arrays
dim3 b(16, 16); // 2D: 16 × 16 × 1 → images, matrices ← our example
dim3 c(4, 4, 4); // 3D: 4 × 4 × 4 → fluid simulation, volumetric data

Rule of thumb: match the shape of your threads to the shape of your data.

For our 128×128 matrix addition:

CUDA C++ dim3 blocks(16, 16); // Grid: 16×16 = 256 blocks
dim3 threads(8, 8); // Block: 8×8 = 64 threads per block
MatAdd<<<blocks, threads>>>(A, B, C);

The <<< >>> is CUDA's launch syntax: <<<grid dimensions, block dimensions>>>. It's what turns a regular function call into 16,384 parallel GPU threads.

Why not dim3 threads(64) instead of (8, 8)? With 64, you'd get threadIdx.x from 0–63 but threadIdx.y always 0 — a flat 1D index. You'd need row = idx / 8; col = idx % 8; to recover 2D position. With (8, 8), CUDA gives you threadIdx.x (0–7) and threadIdx.y (0–7) directly. Same result, cleaner code.

5 The Kernel: What Each Thread Runs

A kernel is a function marked with __global__ that runs on the GPU. Every thread executes the same function but uses its unique indices to work on a different element:

CUDA C++ __global__ void MatAdd(float A[128][128], float B[128][128], float C[128][128]) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;

    C[row][col] = A[row][col] + B[row][col]; // That's it. One line of real work.
}

The highlighted lines are the address calculation — the most important pattern in CUDA. Let's break it down step by step:

1

blockIdx — "Which block am I in?"

The GPU assigns each block a position in the grid. blockIdx.x = column of this block, blockIdx.y = row.

2

blockDim — "How big is each block?"

The number of threads per block in each dimension. Here: blockDim.x = 8, blockDim.y = 8.

3

threadIdx — "Which thread am I within my block?"

Each thread's local position inside its block. Ranges from (0,0) to (blockDim.x-1, blockDim.y-1). In our example that's (0,0) to (7,7) because each block is 8×8.

=

blockIdx * blockDim + threadIdx — Global position

Block offset + local offset = unique position in the full matrix. The same formula works for any grid/block size!

8 Warps: The Hidden Execution Unit

You declare blocks and threads, but the GPU actually executes in groups of 32 threads called a warp. This is the true unit of execution — all 32 threads in a warp execute the same instruction at the same time (SIMT: Single Instruction, Multiple Threads).

Our block has 64 threads. The GPU splits it into 2 warps:

Warp 0: ← threads 0–31
Warp 1: ← threads 32–63
Performance tip: If threads in a warp take different if/else paths, the GPU must execute both paths serially — this is called warp divergence. It's one of the most common CUDA performance pitfalls. Keep your warps doing the same thing!

How are threads assigned to warps?

CUDA flattens the 2D (or 3D) thread indices into a 1D linear index using row-major order, then groups every consecutive 32 into a warp:

Formula // For a 2D block:
linearIdx = threadIdx.y * blockDim.x + threadIdx.x

// For a 3D block:
linearIdx = threadIdx.z * blockDim.y * blockDim.x + threadIdx.y * blockDim.x + threadIdx.x

warpId = linearIdx / 32
laneId = linearIdx % 32 // position within the warp (0–31)

Concrete example with our 8×8 block:

threadIdx (x,y) linearIdx Warp Lane

Notice the pattern: the first 4 complete rows (y=0–3, each 8 threads wide) fill warp 0 with 4×8 = 32 threads. The next 4 rows (y=4–7) fill warp 1. This means threads that are spatially close in the y-dimension end up in the same warp — which matters for memory coalescing and divergence.

Why 32? The warp size of 32 is baked into NVIDIA hardware — it's the width of the SIMT execution unit on every SM. It hasn't changed since the very first CUDA GPU (Tesla, 2006). All current and announced NVIDIA architectures use 32-thread warps. AMD GPUs use 64-thread "wavefronts" instead.
↓

9 How the Hardware Actually Runs It

You asked for 16,384 threads, but even NVIDIA's most powerful GPUs have a finite number of cores. How does this work?

GPU CUDA Cores SMs Waves for 16K threads
RTX 4060 (mainstream) 3,072 24 ~6
RTX 4090 (enthusiast) 16,384 128 ~1
B200 (data center) 18,944 148 ~1

The GPU's warp scheduler handles this automatically. When a warp is waiting for memory (which takes hundreds of cycles), the scheduler instantly swaps in another warp — in zero cycles (no context-switch cost!). This is called latency hiding and is the #1 reason GPUs are fast: they keep cores busy by having thousands of warps ready to go.

The key separation: CUDA separates the logical thread count (what you declare) from physical execution (what the hardware does). You express maximum parallelism; the GPU schedules it efficiently across whatever hardware is available.

Blocks are independent by design. The GPU can run them in any order, on any SM. This is why CUDA scales automatically from a laptop GPU to a data center GPU — more SMs just means more blocks run simultaneously.

blockDim describes the size of each block, not the grid. Since threads(8, 8), blockDim.x = 8 and blockDim.y = 8. The grid dimensions come from gridDim.

row = blockIdx.y * blockDim.y + threadIdx.y = 5 * 8 + 7 = 47. Remember: .y is the row dimension, .x is the column.

Q3: How many warps does a block with 256 threads have?

4
8
16
32
Each warp has 32 threads. 256 / 32 = 8 warps. The GPU schedules these warps independently on the SM's warp schedulers.

Q4: Why can't threads in different blocks use __syncthreads()?

They can — it works across blocks
Different blocks always run at different times
Blocks may run on different SMs with no shared memory
CUDA doesn't support synchronization
Blocks are distributed across different Streaming Multiprocessors (SMs). Each SM has its own shared memory. Since blocks may be on different SMs (or even run at different times), there's no fast shared memory between them and __syncthreads() only works within a block. For cross-block sync, you'd use cooperative groups or atomic operations on global memory.

Q5: You want to process a 1000×1000 matrix with 16×16 blocks. How many blocks do you need?

62 × 62 = 3,844
63 × 63 = 3,969
64 × 64 = 4,096
1000 × 1000 = 1,000,000
ceil(1000/16) = 63. You need 63×63 = 3,969 blocks. Some threads in edge blocks (63×16 = 1008 > 1000) will be "extra" — the kernel should check if(row < 1000 && col < 1000) to avoid out-of-bounds access. This is a very common pattern in real CUDA code.
