CUDA: Grid, Blocks & Threads

How one line of code launches 16,384 parallel workers on a GPU

First — How Many Cores Does a GPU Actually Have?

GPUs have a fixed number of CUDA cores — even NVIDIA's B200, one of the most powerful GPUs, has 18,944 per die. A mainstream GPU might have 2,000–5,000. If you launch more threads than cores available, the GPU schedules them in batches — running a group, then instantly swapping to the next (in nanoseconds). For our 16,384-thread example, a GPU with 4,096 cores would process them in ~4 waves. CUDA separates the logical thread count (what you ask for) from the physical execution (what the hardware does). You declare the work, the GPU figures out how to run it efficiently.

Why organize threads into blocks? GPU hardware is physically organized into groups called streaming multiprocessors (SMs). Each SM runs one or more blocks. Threads within a block can:

  • Share fast memory — 100× faster than global GPU memory
  • Synchronize — wait for each other with __syncthreads()
  • Cooperate — divide sub-problems within the block

Threads in different blocks can't do any of this. The block is the unit of cooperation.

The Code

We want to add two 128×128 matrices together: C = A + B. That's 16,384 additions. On a CPU you'd loop through them one by one. On a GPU, you launch 16,384 threads — one per element — and the GPU schedules them across its available cores in parallel batches. Even if the GPU has fewer than 16,384 cores, it handles the scheduling automatically.

CUDA uses a type called dim3 to define how threads are organized. It always has three components (x, y, z), but unspecified dimensions default to 1. One type covers 1D, 2D, and 3D problems:

dim3 a(256); // 1D: 256 × 1 × 1
dim3 b(16, 16); // 2D: 16 × 16 × 1 ← our example
dim3 c(4, 4, 4); // 3D: 4 × 4 × 4 (e.g. fluid simulation)

For matrix addition we only need 2D, so here's the setup:

dim3 blocks(16, 16); // 16×16 = 256 blocks
dim3 threads(8, 8); // 8×8 = 64 threads per block
MatAdd<<<blocks, threads>>>(A, B, C); // Launch on GPU!

The <<< >>> syntax is CUDA-specific. It means: <<<how many blocks, how many threads per block>>>.

Why dim3 threads(8, 8) instead of just 64? — With 64, you still get threadIdx.x (0–63), but threadIdx.y is always 0 — it's a flat 1D index. To find the row and column you'd need: row = threadIdx.x / 8; col = threadIdx.x % 8;. With dim3(8, 8), CUDA gives you threadIdx.x (0–7) and threadIdx.y (0–7) — a 2D coordinate that maps directly to matrix rows and columns without extra math.

Same for blocks — why blocks(16, 16) instead of 256? — Same idea. With a 2D block layout, blockIdx.x and blockIdx.y give you the block's position in the grid. Combined with thread indices, the matrix position is one clean line: row = blockIdx.y * 8 + threadIdx.y. With a flat 256, blockIdx.y would always be 0 and you'd convert back to 2D yourself. Rule of thumb: match the shape of your threads to the shape of your data.

The Hierarchy

GPUs organize work in three levels. Think of it like a company:

🏢 Grid
The whole company — all the work. Here: 16×16 = 256 departments.
🏠 Block
One department — a team that shares resources. Here: 8×8 = 64 people per team.
👤 Thread
One worker — does exactly one task. Here: adds one matrix element.
📋 The Task
C[row][col] = A[row][col] + B[row][col]
